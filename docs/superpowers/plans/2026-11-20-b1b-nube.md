# B1b — Nube (cuentas, sincronización, propuestas): plan de implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Una API en Cloudflare (Worker + D1) desplegada que guarda canciones, servicios y carpetas de una iglesia, sincroniza por consulta ("lo que cambió después de N"), maneja Líder/Editor/Miembro/compu de confianza y propuestas con aprobación.

**Architecture:** Un solo Worker con **static assets**: sirve la PWA (B1d) y la API bajo `/api/*` en el mismo origen, sin CORS para el celular. La compu llama a la misma URL. La lógica vive en módulos puros que reciben una interfaz `Db` mínima (subconjunto de D1). En pruebas, `Db` se implementa sobre `node:sqlite` (Node 24), así que todo se prueba con Vitest en Node sin miniflare. El código compartido por nube, escritorio y celular (tipos, fusión por campo, diff de letras) va en `shared/`.

**Tech Stack:** Cloudflare Workers + D1 + static assets, wrangler 4, TypeScript, WebCrypto (PBKDF2, SHA-256), Vitest.

**Spec:** `docs/superpowers/specs/2026-11-19-fase-b-alado-conectado-design.md` (secciones 2, 3, 4 y 7). Es la parte B1b de cuatro: B1a (hecha) → **B1b** → B1c (sincronización en la compu) → B1d (PWA).

## Global Constraints

- Todo permiso se valida en el Worker. Ningún dato sale sin sesión válida de la iglesia.
- PIN: PBKDF2-SHA256, 100 000 iteraciones (tope de Workers), sal aleatoria de 16 bytes. Tokens: 32 bytes aleatorios en base64url; en la base solo se guarda su SHA-256.
- Bloqueo: 5 intentos fallidos por (iglesia, nombre) o por (IP, código de iglesia) → 15 min bloqueado.
- Roles: `leader`, `editor`, `member`, `desktop` (compu de confianza). El último Líder activo no se puede desactivar ni degradar.
- Campos de canción sincronizados (cada uno con versión propia): `title, artist, sections, song_key, video_file, text_style, sheet_style, folder_uid`. Editables por Editor solo vía propuesta: `title, artist, sections, song_key, video_file`. Solo `desktop`: `text_style, sheet_style, folder_uid`, carpetas.
- "Gana el último en llegar" por campo. Si el que escribe no había visto la versión vigente de ese campo, se registra un **aviso** para el autor del valor reemplazado.
- Servicios: unidad completa (nombre, fecha, notas, elementos ordenados `{song_uid, custom_video_file}`). Escriben Líder, Editor y `desktop`.
- Borrar canción: solo Líder y `desktop`. Se rechaza si algún servicio no borrado la usa. Si después llega un servicio que la usa, la canción se restaura y se avisa a los Líderes.
- Una canción nueva propuesta no puede ir en un servicio hasta aprobarse: la API rechaza servicios que apunten a canciones inexistentes o borradas.
- URL: `https://alado.<subdominio>.workers.dev` (gratuita). **Ruling de planeación:** se usa un Worker con assets en lugar de Pages + Worker para servir PWA y API en un solo origen. El usuario eligió "gratis", y `workers.dev` lo es.

## Review Focus

1. **Dos dispositivos escriben el mismo campo sin conexión:** gana el último y el otro recibe un aviso con lo reemplazado. Campos distintos no chocan. → pruebas en Task 3.
2. **Un Miembro o Editor llama a la API directamente para escribir lo que no le toca:** debe recibir 403. → pruebas en Task 4.
3. **Fuerza bruta de PIN o código:** bloqueo tras 5 intentos, incluso con un PIN correcto mientras dura. → prueba en Task 2.
4. **Aprobar una propuesta cuya canción cambió después:** la respuesta y la bandeja lo indican (`stale: true`); aprobar aplica solo los campos propuestos. → prueba en Task 5.
5. **Cambiar el código de iglesia:** las sesiones de Miembro viejas dejan de funcionar; las de Líder y Editor no. → prueba en Task 2.

### Task 2: Autenticación, sesiones y administración de usuarios

**Files:**
- Create: `cloud/src/crypto.ts` (`hashPin`, `verifyPin`, `randomToken`, `sha256`, `randomCode`)
- Create: `cloud/src/auth.ts`
- Test: `cloud/test/auth.test.ts`

**Interfaces:**
- Produces (todas reciben `db: Db` y devuelven `{ ok: true, ... } | { ok: false, status, error }`):
  - `setupChurch(db, { churchName, leaderName, pin, deviceName })` → `{ churchCode, recoveryCode, deviceToken }`. Solo si no existe ninguna iglesia; si ya existe, 409.
  - `login(db, ip, { churchCode, name, pin })` → `{ token, role, userId, name }`.
  - `loginMember(db, ip, { churchCode })` → `{ token, role: 'member' }`.
  - `createLinkCode(db, session)` (Líder) → `{ code }`: 6 dígitos, válido 10 min, un solo uso.
  - `linkDevice(db, ip, { code, deviceName })` → `{ deviceToken, churchName }`.
  - `authenticate(db, bearer)` → `Session | null`, con `Session = { churchId, role, userId?, deviceId?, name }`. Una sesión de miembro con `code_version` viejo devuelve `null`.
  - `listUsers` / `createUser` / `updateUser(db, session, id, { role?, pin?, active? })` (Líder). Guardia del último Líder activo.
  - `rotateChurchCode(db, session)` (Líder) → `{ churchCode }` e incrementa `code_version`.
  - `recover(db, ip, { churchCode, recoveryCode, leaderName, newPin })`.
  - **Ruling de planeación:** se permite en cualquier momento con el código de recuperación, que se imprime y se guarda. El spec dice "si no queda otro Líder", pero no hay forma confiable de saberlo.
- Formato del código de iglesia: 8 caracteres de `ABCDEFGHJKMNPQRSTUVWXYZ23456789`, mostrado como `XXXX-XXXX` y aceptado sin guion ni mayúsculas. Código de recuperación: 16 caracteres del mismo alfabeto.

### Task 3: Fusión por campo y protocolo de sincronización

**Files:**
- Create: `shared/merge.ts` (puro)
- Test: `shared/merge.test.ts`
- Create: `cloud/src/sync.ts`
- Test: `cloud/test/sync.test.ts`

**Interfaces:**
- Produces: `mergeSongFields(server: { fields, versions, authors }, change: { fields: Partial<SongFields>, seen: Partial<Record<SongField, number>> }, author: { id: string; name: string }, seq: number) → { fields, versions, authors, replaced: { field, previousAuthorId, previousValue }[] }`.
  - Un campo se considera **reemplazado sin haberlo visto** cuando `seen[f] < versions[f]` y el autor anterior es otro.
- Produces: `pull(db, session, since: number) → { seq, songs: SyncSong[], folders: SyncFolder[], setlists: SyncSetlist[], notices: Notice[] }`.
  - Los avisos se marcan como entregados al leerlos.
  - Para Miembros no salen `text_style`/`sheet_style` (no los necesitan); todo lo demás sí.
- Produces: `push(db, session, changes: Change[]) → { seq, results: ({ ok: true } | { ok: false; error: string })[] }`.
  - Tipos de `Change`:
    - `{ kind: 'song', uid, fields, seen }`;
    - `{ kind: 'song-delete', uid }`;
    - `{ kind: 'setlist', uid, data, seenSeq }`;
    - `{ kind: 'setlist-delete', uid }`;
    - `{ kind: 'folder', uid, name }`;
    - `{ kind: 'folder-delete', uid }`.
  - Cada cambio aceptado incrementa `churches.seq` y estampa la fila.
  - Avisos: para el autor del valor reemplazado (`target` = `user:<id>` o `device:<id>`). Texto: *"Tu cambio de «{campo}» en «{título}» fue reemplazado por uno más reciente de {nombre}."* Para servicios: *"Tu versión del servicio «{nombre}» fue reemplazada por una más reciente de {nombre}."*
  - Nombres de campo en español en los avisos: `title`→título, `artist`→artista, `sections`→letra, `song_key`→tono, `video_file`→video, `text_style`→estilo, `sheet_style`→hoja PDF, `folder_uid`→carpeta.

    - `same author overwriting its own value is not a conflict`;
    - `seen up to date is not a conflict`.
  - **`cloud/test/sync.test.ts`:**

    - `deleting a song used by a setlist is rejected`;
    - `a late setlist that uses a deleted song restores it and notifies leaders`;

### Task 5: Propuestas y aprobación

**Files:**
- Create: `shared/lyricsDiff.ts` (diff de líneas por sección para la bandeja: `diffSections(before, after) → { label, lines: { kind: 'same' | 'added' | 'removed', text }[] }[]`)
- Test: `shared/lyricsDiff.test.ts`
- Create: `cloud/src/proposals.ts`
- Test: `cloud/test/proposals.test.ts`

**Interfaces:**
- `propose(db, session /*editor*/, { song_uid | null, fields, seen })` → `{ id }`.
  - Con `song_uid` null es una canción nueva, y exige `title`.
- `listProposals(db, session, { status? })`:
  - el Líder ve todas;
  - el Editor solo las suyas.
  - Cada una trae `{ ...proposal, current: SongFields | null, stale: boolean }`. `stale` es verdadero si alguna versión de los campos propuestos subió desde `seen`.
- `decide(db, session /*leader*/, id, { action: 'approve' | 'reject', note? })`.
  - Aprobar aplica los campos como un cambio del Líder, pasando por `mergeSongFields` con `seen` = las versiones actuales, sin aviso de conflicto. Una canción nueva se crea con un uid nuevo.
- `withdraw(db, session /*autor*/, id)`.
- `pendingCount(db, session)`.

  - `reject changes nothing`;
  - `stale is true when the song changed after the proposal`;
